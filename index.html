Build, run and govern an agent — 7 labs, in order

The main track, and the one most people want. Build one, run it in production, hand the building to a coding agent, measure it, secure it, publish it — then the capstone carries a single agent through every stage at once.

1 Google Cloud ADK lab Build an agent that behaves. A docstring decides whether a tool is ever chosen, a four-character prefix decides whether data leaks, and model-written code runs in a room with no doors. Ten tabs from first agent to production routing. 10 tabs · 11 simulations · three Google courses
2 AWS AgentCore lab What it takes to trust an agent in production: isolation, identity, tools, memory, and proving it works. Watch a request become a trace and a prompt change fail a quality gate. 9 tabs · 10 simulations · scenario drill
3 Google Cloud Agents building agents A coding agent writes your agent from a specification — and quietly targets the wrong API if you skip a step. Then a managed runtime that starts locked down. Watch the drift, the eval trap and the containment layers. 9 tabs · 10 simulations · two Google courses
4 Google Cloud Evaluation & hill climbing An agent gives a different answer every time, so “it works” stops being something you can assert. Score it, find the turn that actually broke, then climb: change one thing, measure everything, keep it or throw it away. 11 tabs · 14 simulations · five Google courses
5 Google Cloud Govern & secure agents Every security control assumes a person or a program on the other side. An agent is neither — it decides what to do by reading text, and text can be written by an attacker. The gateway on both sides, identity that expires, and the injection nobody has to break in for. 12 tabs · 12 simulations · two Google courses
6 Google Cloud Gemini Enterprise rollout Half plumbing, half people. Which identity provider your data sources force on you, the connector whose default is “everyone sees everything”, the firewall that cuts answers off at thirty seconds, and getting several thousand colleagues to actually use it. 12 tabs · 14 simulations · five Google courses
7 Google Cloud Peak Week — one agent end to end A sorter fails at a parcel hub on the busiest night of the year. Every other lab teaches one stage of an agent’s life; this one carries a single agent through all of them — made, deployed, secured, scored, handed over — so the handoffs are visible: the small file you paste in at stage two is what makes it publishable at stage five, and its permissions are the one thing deploying does not sort out for you. 10 tabs · 16 simulations · groundwork → work → survive → safe → good → theirs

Cloud and architecture — 4 labs, in order

How the cloud actually works, how to draw it so somebody else can act on it, and then the two exam workbenches. Useful on its own, and the ground the agent track is standing on.

1 AWS Azure Google Cloud Cloud lab Follow one request from phone to database, break it, and see which layer stops it. Then the OSI stack with 94 cloud services placed on it, a landing zone you can click apart, VPC sizing and public-versus-private, a VPC simulator, NGINX, IAM, and a three-cloud translator. 14 tabs · 27 diagrams · 30 simulations · 94 services mapped
2 AWS Azure Google Cloud Architecture diagrams Most diagrams are drawn for the person who drew them. Find eight defects in a real-looking one, break each dependency to see what the happy path never said, and take the eight questions a reviewer always asks. 11 tabs · 11 simulations · a synthesis, not a course
3 Google Cloud GCP Architect exam A case-study exam, so several answers work and one clause rules the others out. Sort a case into what actually binds you, work one end to end, and meet the option that is technically fine and still wrong. case workbench · 4 simulations
4 AWS SAP-C02 cheatsheet 53 trigger phrases and what each one is really asking for, a drill that only clears a card after two clean passes, and the traps that appear as options anyway. trigger drill · decision tables

Under the hood — 4 labs, in order

The layers everything above is running on. Optional depth rather than a prerequisite — take it whenever you want to know why inference is priced the way it is, and read it in order.

1 AWS Azure Google Cloud The machine underneath Why inference gets cheaper when you batch it, why a model that “fits in 40 GB” does not, and why the expensive card is idle most of the time — all the same question. Warps, the memory ladder, the roofline, coalescing, tiling, tensor cores and the attention matrix that is never written down. 10 tabs · 13 simulations · worked on a named machine
2 AWS Azure Google Cloud One token at a time A model does one thing: score every possible next token. Watch the loop run, text become tokens, a pronoun find its noun, the KV cache turn quadratic into linear — and then work out, on real models, why the cache ends up bigger than the weights. 11 tabs · 20 simulations · arithmetic on named models
3 AWS Azure Google Cloud The engine, not the model You can run a model in four lines. Serving one is a scheduler, an allocator, a cache and an admission controller — and almost none of it is machine learning. Prefill against decode, preemption, prefix caching, speculative decoding, CUDA graphs, multi-LoRA, and why your mean latency is lying to you. 10 tabs · 10 simulations · systems, not modelling
4 AWS Azure Google Cloud Twenty engines, one endpoint An engine schedules its own GPU and cannot see the other nineteen. Which worker gets this request, does one already hold the prefix, is it cheaper to move that state or recompute it, and what does someone watching a stream see when its worker dies. 9 tabs · 9 simulations · above the engine
